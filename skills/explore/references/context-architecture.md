# Context architecture — building, budgeting, and refreshing the orchestrator's context

How the orchestrator decides *what it knows, when* — composing, bounding, and refreshing its own context deliberately instead of front-loading everything and hoping. Adopted from the dsh (deepseek-harness) disciplines — baseline instruction composition, budget-then-truncate refresh, spill behind opaque locators, deferred capability loading — and from the cordis / "A Programming Paradigm for Spatiotemporal Composability" pairing of cleanup-on-exit with declared dependencies (paper abstract); the runtime machinery there is non-portable to a markdown skill, but the disciplines are. On a Knoxville-linked repo the fragment sources are vault relPaths served through the `docs_*` tools; elsewhere they degrade to ordinary repo doc paths — same kinds, same rules, different root.

**Fragment kinds.** A context fragment is a doc — a vault relPath or a repo path — or a named section of one, held as a typed **pointer**: what it is, plus the condition that loads it. The pointer wording carries the trigger, so the list itself is readable without loading anything.

| Kind | Loads when | Canonical members |
|---|---|---|
| `baseline` | always, at the orientation pass | the vault index → the overview / `agents/` mirror (`docs/system-design-reference/agents/README.md`) → the plans digest (`plans/agents/README.md`) — broad → specific |
| `lens` | the phase that owns it runs | `references/architecture-patterns.md` for Phase-2 exploration, `references/audit-playbook.md` for `--improve`/`--security`, `references/plan-template.md` for Phase-4 planning |
| `quirk` | a dispatch rides that lane | the per-lane quirk blocks in `references/delegation-transports.md` — the opencode-lane quirks, the stale-transport table, the shell/MCP call shapes |
| `deferred` | its named load-condition surfaces | any fragment a plan names for a situation — declared up front, pulled on encounter, never carried speculatively |

**The orientation pass (Phase 0.5).** After recon (Phase 1) and before the Phase-2 fan-out, the orchestrator composes its baseline: broad → specific (vault index → overview/mirror → plans digest), byte-identical content deduplicated (the mirror and the digest often repeat the index's rows — one copy only), bounded by budget. Budget pressure resolves **broad-first**: omit a broader file entirely before truncating a more specific one, and **never summarize instructions** — a paraphrased rule is a different rule, so a fragment that doesn't fit whole is dropped, not condensed (the dsh agent-instructions rule, carried verbatim). Then — before any dispatch — the composed fragment list is **written into the run record**: one line per fragment with its relPath, why it was loaded, and its byte count, so the operator can review that the constructed context will shape the run as intended before the spend starts.

**Deferred fragments in plans.** A plan lists the fragments its executor might need per situation — *"wrapper misbehaves → `delegation-transports.md` stale-transport table"* — as named pointers with their load-conditions, not as inlined content. The executor pulls the fragment when it encounters the condition instead of carrying every contingency from dispatch. This keeps the brief small (a brief inlines only what the common path needs — Hard Rule 3's self-containment applies to the *path*, not to every branch) and keeps the exceptional-path doctrine in one authoritative place rather than copied, and copied wrong, into every plan.

**Model-visible ⟺ logged.** Whatever shaped a dispatch brief must be reconstructable from the run record (the dsh invariant): the brief cites its fragments by relPath, every steer sent mid-run is recorded with its target and reason, and every deferred pull notes the condition that triggered it. A reviewer reading only the record can rebuild what any model in the run could see — no "as discussed" context that lives only in the orchestrator's head (Hard Rule 3, applied to the record itself). The orientation-pass fragment list is the record's anchor: it is what makes the rest auditable, since every later citation resolves against a list the operator already reviewed.

**Spill.** Worker output beyond a stated budget never enters the orchestrator's context inline. It goes to a scratch file (the same scratch discipline as report capture — a directory this skill owns, never the user's tree), and the report carries an **opaque locator plus a one-line retrieval hint** — `spill: .explore-scratch/<run>/worker-3-report.md — full lens dump; read on demand` — so the orchestrator pays for the finding, not the transcript, and can still reach the raw output when vetting needs it (dsh spill pattern). Phase-3 vetting is the sanctioned consumer of spilled bytes: the verdict reads the finding, the vet pulls the spill. Nothing else should.

**Touch-driven refresh.** After an executed diff lands (an `--execute-level` round, a `--reconcile` write), the baseline is *not* recomposed wholesale. Only fragments whose sources changed are re-read before the next dispatch that uses them: an executed plan's diff touching mapped files refreshes the overview/mirror fragment; a plan status change refreshes the plans digest; a lane quirk file edited mid-run refreshes that quirk. Untouched fragments keep their loaded bytes. Refresh is scoped by touch, never by timer.

**Enablement.** This architecture is per-machine, opt-in: the `--setup-plugin` wizard offers it as a step (wired alongside the roster persistence — `references/setup.md`), and enablement is recorded as `optimizations.context_architecture: {applied_at, enabled}` beside `optimizations.omp_roles` in the saved config — one additive key, readers ignore unknown keys, so old readers are unaffected. Absent the key, the skill behaves exactly as before: recon reads what recon reads, briefs carry what briefs carry, and no fragment list, spill locator, or refresh rule is consulted. Nothing here is a default.
